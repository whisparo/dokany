🏛️ دكاني — المعمارية النهائية للواجهة الأمامية والمخزون الحي (v3.0)
Data‑Driven Single‑Snapshot Storefront Architecture
مع Double‑Cache كطبقة تخزين مؤقتة حية (Edge‑Native Living Cache)
📜 الديباجة: فلسفة "البيانات حية على الحافة"
في هذا المخطط، نتعامل مع الـ Double Cache (Cloudflare KV + IndexedDB) كطبقة تخزين مؤقتة حية (Living Temporary Storage) تعتمد عليها المتاجر في جميع العمليات الحيوية:

جميع عمليات القراءة (بدون أي استعلام على D1).

عمليات التعديل اللحظية مثل خصم المخزون أثناء الـ Checkout.

تحديث لوحة تحكم التاجر بزمن استجابة 0ms.

قاعدة البيانات (D1) ليست مصدراً للحقيقة، بل هي مجرد أرشيف بارد (Cold Archive) لتخزين الطلبات المنجزة فقط.
لا تحتوي D1 على أي بيانات مخزون أو حالة حية، ولا يتم تحديثها أثناء التشغيل المباشر. جميع التعديلات على المخزون والأسعار والحالة الحيوية تتم حصرياً في الـ Double Cache.

🎯 المبادئ المعمارية الحاكمة
المبدأ	التوضيح
Single Snapshot	يتم بناء ملف JSON واحد يحتوي على كامل هيكل المتجر (أقسام، منتجات، محتوى الصفحة) عند حفظ التغييرات من لوحة التحكم.
Living Double‑Cache	Cloudflare KV (نسخة الحافة) + IndexedDB (نسخة العميل) هما المصدران الوحيدان للحقيقة للمخزون والأسعار والحالة الحيوية للمتجر.
Atomic Stock Deduction	خصم المخزون يتم مباشرة في الـ Double‑Cache (بدون العودة إلى D1)، مع تحديث فوري للمفتاح store:{slug}:stock:{productId}.
Version‑Based Invalidation	يتعرف العميل على الإصدار الجديد من خلال HEAD request خفيف، ولا يُعيد تحميل Snapshot إلا عند التغيير الفعلي.
Auto Warm‑up & Rollback	في حال فقدان الكاش أو فشل بناء Snapshot جديد، يتم إعادة البناء تلقائياً من D1 و KV مع الاحتفاظ بالنسخة القديمة كـ Fallback.
Periodic Order Archiving	يتم نقل الطلبات من Buffer (KV) إلى D1 عبر Cron Job دوري (كل 5 دقائق) لتخزينها كأرشيف نهائي. لا يتم تحديث المخزون في D1 مطلقاً.
Zero‑Cost by Design	جميع المكونات ضمن حدود Cloudflare و Upstash المجانية (Workers, KV, D1, Cron).

2. المفاتيح الحيوية (Live Micro‑State Keys)
تُخزَّن بشكل منفصل في نفس KV Namespace، وتُحدَّث بشكل ذري وبتكرار عالٍ. هذه هي المصادر الوحيدة للحقيقة للحالة الحيوية:

المفتاح	القيمة	التحديث
store:{slug}:stock:{productId}	العدد المتبقي (integer)	عند كل عملية شراء ناجحة
store:{slug}:price:{productId}	السعر الحالي (integer)	عند تغيير التاجر للسعر (نادر)
store:{slug}:stats	{ salesCount, orderCount, revenue }	عند كل عملية شراء ناجحة
store:{slug}:status	active / maintenance	عند تغيير حالة المتجر
⚠️ ملاحظة: D1 لا تحتوي على أي من هذه المفاتيح.
المخزون والأسعار والحالة تُدار حصرياً في الـ Double Cache.

🔄 تدفق البيانات الكامل (End‑to‑End Flow)
أ. مرحلة التعديل (Dashboard Phase)
المشغل: التاجر يحفظ التغييرات في لوحة التحكم.

التدفق:

التاجر يضيف/يعدل أقساماً، منتجات، أو محتوى الصفحة في لوحة التحكم.

يتم الحفظ في D1 (كمرجع تاريخي للبيانات الهيكلية).

يُطلق Server Action لتشغيل Orchestrator:

يقرأ البيانات من D1.

يبني Snapshot JSON موحداً.

يتحقق من صحته عبر Zod.

يكتبه في KV تحت مفتاح store:{slug}:v{version}.

يحدِّث المؤشر store:{slug}:latest ليشير إلى الإصدار الجديد.

يزيد رقم الإصدار (يتاح للعميل عبر HEAD request).

ملاحظة: لا يتم تحديث المخزون أو الأسعار في D1 أثناء هذه المرحلة.

ب. مرحلة العرض للزبون (Storefront Phase)
المشغل: يزور العميل المتجر (أول زيارة أو عودة).

التدفق:

يزور العميل المتجر.

يُرسل الـ Client Bootstrapper طلب HEAD إلى /api/snapshot/{slug} مع If‑None‑Match: v{current}.

يرد الـ Worker:

بـ 304 Not Modified إن كان الإصدار نفسه → يستخدم العميل النسخة المخزنة في IndexedDB (0ms).

بـ 200 OK مع Snapshot الجديد إن تغير الإصدار.

يقوم العميل:

بتخزين الـ Snapshot في IndexedDB.

بقراءة المفاتيح الحيوية (stock:{productId}, price:{productId}) مباشرة من KV (أو من IndexedDB إن كانت مخزنة مسبقاً).

بعرض الصفحة فوراً باستخدام البيانات المحلية.

ملاحظة: لا يتم أي استعلام على D1 أثناء هذه المرحلة.

ج. عملية الشراء (Checkout & Stock Deduction)
المشغل: العميل يضغط "تأكيد الطلب".

التدفق التفصيلي:

العميل يضغط "تأكيد الطلب".

الـ Worker يستقبل الطلب ويتحقق من صحة البيانات (Zod + Fraud Protection):

فحص qty > 0.

فحص عدم وجود منتجات مكررة.

فحص totalAmountInt مطابق لـ sum(priceInt * qty).

فحص idempotencyKey بصيغة UUIDv4 صحيحة.

يدخل في بلوك Atomic Rollback:

يقرأ المخزون الحالي من KV: store:{slug}:stock:{productId}.

إذا كان المخزون كافياً:

ينفذ Atomic Decrement عبر KV.put().

يكتب الطلب في Buffer (pending_order:{storeId}:{idempotencyKey}).

يحدِّث إحصائيات المتجر في KV (store:{slug}:stats).

يرد بـ 200 OK (زمن استجابة < 10ms).

إذا كان المخزون غير كافٍ:

يرد بـ 409 Conflict مع رسالة "نفدت الكمية".

إذا فشل KV.put() للطلب:

ينفذ Rollback فوراً (إعادة المخزون).

يرد بـ 500 Internal Server Error.

في الخلفية (Async via ctx.waitUntil):

يُرسل إشعار Telegram للتاجر (بـ HTML Mode).

يُحدث الـ Double Cache للداشبورد (إحصائيات حية).

ملاحظة: لا يتم كتابة أي شيء في D1 أثناء هذه المرحلة. كل العمليات تتم في KV فقط.

د. المزامنة الدورية (Periodic Order Archiving) — الـ Cron Job
المشغل: الـ Cron Job يعمل كل 5 دقائق.

التدفق التفصيلي:

يجلب جميع الطلبات المعلقة:

ينفذ list() مع Retry (3 محاولات) مع do-while و cursor لسحب كل المفاتيح pending_order:*.

في حال فشل list() بعد 3 محاولات:

يُسجل الخطأ في dead_letter_batches.

يُرسل تنبيه للمطورين (Telegram).

يُوقف الدورة دون مسح أي بيانات.

يقطّع الطلبات إلى دفعات (Batches):

كل دفعة لا تتجاوز 200 طلب.

لكل دفعة (مع In-Cycle Retry):

ينفذ env.DB.batch() مع INSERT OR IGNORE لمنع التكرار بناءً على idempotency_key.

إذا فشلت الدفعة:

3 محاولات مع Exponential Backoff (500ms, 1s, 2s).

بعد الفشل، تُترك المفاتيح في KV وتُسجل في DLQ.

بعد نجاح الدفعة:

يمسح مفاتيح الـ 200 طلب المعالجة من KV.

لا يقوم بتحديث المخزون في D1 لأن المخزون يُدار حصرياً في KV.

في حال فشل الدفعة نهائياً:

تُترك المفاتيح في KV.

يُسجل الفشل في dead_letter_batches.

تُعاد المحاولة في الدورة القادمة.

ملاحظة: D1 لا تحتوي على أي بيانات مخزون، ولا يتم تحديثها أثناء الـ Cron Job. دورها فقط هو تخزين الطلبات المنجزة كأرشيف نهائي.

هـ. التعافي من الفشل (Auto Warm‑up & Rollback)
المشغل: Cache Miss أو فشل بناء Snapshot.

التدفق التفصيلي:

1. Auto Warm‑up (فقدان الكاش)
typescript
async function getSnapshot(storeSlug: string, env: Env): Promise<Snapshot> {
  // 1️⃣ محاولة القراءة من KV
  const latestKey = await env.KV.get(`store:${storeSlug}:latest`);
  const snapshot = await env.KV.get(`store:${storeSlug}:${latestKey}`);

  if (snapshot) {
    return JSON.parse(snapshot);
  }

  // 2️⃣ Auto Warm-up: إعادة بناء الـ Snapshot من D1 (البيانات الهيكلية فقط)
  console.warn(`⚠️ Cache miss for ${storeSlug}, rebuilding...`);
  const newSnapshot = await rebuildSnapshot(storeSlug, env);
  const newVersion = Date.now();

  // 3️⃣ كتابة الـ Snapshot الجديد في KV (ذرية)
  await env.KV.put(`store:${storeSlug}:v${newVersion}`, JSON.stringify(newSnapshot));
  await env.KV.put(`store:${storeSlug}:latest`, `v${newVersion}`);

  return newSnapshot;
}
2. Rollback (فشل بناء Snapshot)
typescript
async function buildSnapshot(storeId: string, env: Env): Promise<void> {
  const oldVersion = await env.KV.get(`store:${storeId}:latest`);
  const oldSnapshot = await env.KV.get(`store:${storeId}:${oldVersion}`);

  try {
    // محاولة بناء Snapshot جديد (من D1)
    const newData = await fetchStoreData(storeId);
    const newSnapshot = buildJSONTree(newData);
    const newVersion = (parseInt(oldVersion) || 0) + 1;

    // كتابة الـ Snapshot الجديد
    await env.KV.put(`store:${storeId}:v${newVersion}`, JSON.stringify(newSnapshot));
    await env.KV.put(`store:${storeId}:latest`, `v${newVersion}`);

  } catch (error) {
    // 🛡️ Rollback: الإبقاء على الإصدار القديم
    console.error(`❌ Snapshot build failed for ${storeId}:`, error);

    // تسجيل الفشل في DLQ
    await env.DB.prepare(
      `INSERT INTO snapshot_failures (store_id, version, error, created_at) VALUES (?, ?, ?, ?)`
    ).bind(storeId, oldVersion, error.message, Date.now()).run();

    // إرسال تنبيه للمطورين
    await sendTelegramAlert(env, `🚨 Snapshot build failed for store ${storeId}`);
  }
}
ملاحظة: لا يتم التعامل مع المخزون في D1 أثناء التعافي، لأن المخزون يُستعاد من KV أو يُحسب من الطلبات المُجمَّعة في D1.

✅ الخلاصة النهائية
هذه المعمارية (v3.0) تقدّم نقلة نوعية في كيفية بناء واجهات المتاجر المعتمدة على Edge:

تعتمد على Snapshot واحد يُخزَّن في KV ويُنسَخ إلى IndexedDB.

تتعامل مع المخزون والأسعار كبيانات حية تُحدَّث لحظياً في الكاش دون الحاجة إلى D1.

تفصل بين البيانات الهيكلية (نادراً ما تتغير) والبيانات الحيوية (المتغيرة باستمرار).

تزامن دوري مع D1 يقتصر على نقل الطلبات المنجزة فقط (بدون أي تحديث للمخزون).

تكلفة صفرية واستخدام مثالي لحدود الخدمات المجانية.

لا توجد أي مشغلات (Triggers) على قاعدة البيانات؛ D1 هي مجرد مستودع سلبي للطلبات.

بهذا، تحقق دكاني سرعة الـ 0ms في عرض المتجر، ودقة الـ 10ms في معالجة الطلبات، وموثوقية المؤسسات مع $0 تكلفة تشغيلية. 🚀
