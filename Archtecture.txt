📜 الديباجة — فلسفة "المحرك الخالد المُحكَم"

هذه المعمارية هي نتاج رحلة معماريّة عميقة، تجمع بين الرؤية النظرية والتنفيذ العملي، مع الأخذ بعين الاعتبار حدود الخدمات المجانية، وسيناريوهات الفشل، وقابلية التوسع. إنها ليست مجرد بنية تحتية، بل نظام بيئي متكامل يعمل بتناغم تام بين مكوناته، مع تغطية كافة سيناريوهات الطوارئ والحدود القصوى للخدمات المجانية.

✨ المبادئ الحاكمة الإحدى عشرة

العزل الفيزيائي
كل مجموعة من التجار (١٥ تاجر) في قاعدة D1 مستقلة.

الفصل التام
Core DB ونظام الأوديت والتحليلات نظامان مستقلان تماماً.

التوسع العضوي
نبدأ بقاعدة D1 واحدة ونضيف القواعد تدريجياً حسب الحاجة.

المعالجة الهجينة
العمليات الحرجة (مخزون، دفع) متزامنة (Sync)، والعمليات الثانوية (إشعارات، أرشفة) غير متزامنة (Async).

Idempotency الشاملة
كل عملية قابلة للتكرار بأمان، مع قفل موزع هجين (Redis + D1) لمنع السباقات.

التوجيه اللامركزي
كل Worker يوجه الطلبات بنفسه، دون نقطة فشل واحدة.

المبدأ السابع: معمارية العميل أولاً والنبضة الحية (Client-First & Pulse Architecture)
المتاجر تُخدم كـ "مرآة محليّة فائقة السرعة" (Store Replica) تُخزن في ذاكرة متصفح الزبون (IndexedDB) مع تسخين الكاش عند أول زائر (Warm-up Cache). المتجر يفتح في 0ms ويُحدث بياناته عبر "نبضات خفيفة" (Pulse Events) من الباك إند عند حدوث أي تعديل. العمليات التحليلية المعقدة تُحمل عند الطلب فقط (Lazy-Loaded) داخل تابات مستقلة لضمان تجربة خفيفة على أضعف الموبايلات.

المراقبة والمناعة الذاتية
نظام متكامل للمقاييس، السجلات، والتنبيهات، مع آلية للتعامل مع الرسائل السامة (Poison Messages).

التكلفة الصفرية المطلقة
جميع المكونات ضمن حدود الخدمات المجانية، مع مراقبة دقيقة للاستهلاك.

الأمان متعدد الطبقات
عزل فيزيائي ومنطقي، تشفير، ومصادقة ثلاثية القنوات (تليجرام، بريد إلكتروني، PIN احتياطي).

الحصن الرقمي
Rate Limiting متعدد الطبقات (٤ طبقات) في Worker مستقل — الدفاع المتدرّج بالتكلفة الصفرية.

2.3 طبقة التوجيه (اللامركزية)

آلية التوجيه:

استخراج store_id من JWT أو من الطلب.

البحث في In-Memory Cache: خريطة store_id → database_id (تُحدّث كل 5 دقائق).

إذا لم يُوجد: البحث في Redis Cache.

إذا لم يُوجد: البحث في KV (المصدر الدائم).

إذا لم يُوجد: استخدام Consistent Hashing مع Virtual Nodes كـ Fallback (يُفعّل فقط عند وجود 50+ قاعدة).

توجيه الطلب إلى قاعدة D1 المناسبة (env[DB_${databaseId}]).

2.4 طبقة الـ Idempotency المركزية (مع قفل موزع)

المبدأ: كل عملية تحمل Idempotency Key، تُخزّن في جدول idempotency في D1.

آلية العمل:

مرحلة الحافة الذرية: يُنفذ Worker أمر SET lock:idempotency:{key} pending EX 30 NX على Upstash Redis. إذا فشل الأمر: يُرفض الطلب فوراً بـ 409 Conflict. إذا نجح: يتم الانتقال للمرحلة التالية.

مرحلة التحقق الدائم: يبدأ Worker ترانزاكشن في D1 ويستعلم عن المفتاح في جدول idempotency. إذا كان completed: يُحذف قفل Redis، وتُعاد النتيجة المخزنة. إذا كان failed: يُحدَّث السجل إلى pending ويُمدَّد قفل Redis. إذا لم يوجد: يُنشأ سجل جديد بحالة pending.

بعد المعالجة: نجاح: تحديث الحالة إلى completed مع النتيجة، وحذف قفل Redis. فشل: تحديث الحالة إلى failed وحذف قفل Redis للسماح بالمحاولة الفورية.

⚠️ تنبيه أمني: تأكد من أن الـ Worker الحالي هو نفسه الذي أنشأ القفل (باستخدام UUID فريد كقيمة للقفل) لتجنب حذف قفل أنشأه Worker آخر.

سياسة TTL:

نوع العملية	TTL
حرجة (دفع، مخزون، طلبات)	24 ساعة
عادية (إشعارات، تحديثات)	1 ساعة
ثانوية (أرشفة، تقارير)	1 ساعة
2.5 طبقة المعالجة المباشرة (Direct Write Architecture)

الفلسفة الجديده: بفضل تحييد 99% من عمليات القراءة عبر "المرآة"، أصبحت قاعدة البيانات D1 متفرغة تماماً، مما يغنينا عن استخدام الطوابير المعقدة (Cloudflare Queues) وإعادة الترتيب بـ sequence_number لعمليات الشراء والتعديل.

الكتابة المباشرة (Direct Sync Write): طلبات الشراء وتعديل البيانات تُكتب مباشرة في D1.

التعافي عند الانشغال (Exponential Backoff): في حال حدوث تضارب لحظي نافر أثناء كتابة الطلب، ينفذ الـ Worker محاولة إعادة كتابة تلقائية بعد (50ms → 100ms → 200ms) وتنجح العملية بسلاسة دون أن يلاحظ الزبون.

استخدام الطوابير (Queues Limit): يقتصر استخدام Cloudflare Queues فقط على المهام غير اللحظية إطلاقاً (مثل إرسال الإيميلات، توليد الفواتير PDF، وإرسال إشعارات تليجرام).

2.6 طبقة إدارة الـ Schema

المبدأ: تطبيق تغييرات Schema تدريجياً (Progressive Rollout).

آلية العمل:

Schema Versioning: جدول schema_version في كل قاعدة.

Canary Deployment: تطبيق التغيير على قاعدة واحدة أولاً، مراقبة لمدة ساعة، ثم تطبيق تدريجي.

Idempotent Migrations: استخدام IF NOT EXISTS و IF EXISTS.

تسجيل الفشل: في KV (failed_migrations:{db_id} → migration_version).

جدولة الـ Migration: أسبوعياً (عبر QStash) أو عند الحاجة (عبر واجهة إدارية).

2.7 طبقة التخزين المؤقت (Cache)

استراتيجية Cache-Aside:

القراءة: استعلم من Redis → إذا لم يوجد، استعلم من D1 → خزّن في Redis مع TTL.

الكتابة (Sync): اكتب في D1 → احذف من Cache.

الكتابة (Async): اكتب في D1 → احذف من Cache → TTL قصير (30 ثانية).

TTL ديناميكي:

بيانات متغيرة كثيراً (مخزون): 30 ثانية.

بيانات متغيرة قليلاً (منتجات): 5 دقائق.

بيانات ثابتة (أسماء المتاجر): 1 ساعة.

حماية Cache Stampede:

عند انتهاء Cache، يستخدم Worker SETNX مع TTL 5 ثوانٍ للحصول على Lock.

إذا نجح: يجلب البيانات من D1 ويخزّنها.

إذا فشل: ينتظر (Exponential Backoff: 200ms, 400ms, 800ms) ثم يقرأ Cache (Stale-While-Revalidate).

Cache Invalidation:

Sync: حذف Cache المرتبط (DEL key).

Async: Cache TTL قصير (30 ثانية).

Purge يدوي: عبر API Endpoint محمي.

2.8 معمارية المرآة المزدوجة والعداد الذري (Dual Replica & Atomic Engine)

أ. مرآة الحافة للزوار الجدد (Edge Snapshot):

عند دخول أول زائر لمتجر معين، يقوم Worker بجمع بيانات المتجر (المنتجات، الأسعار، الصور) في ملف JSON موحد ويخزنه على Edge CDN (Stale-While-Revalidate).

جميع الزوار التالين (من الزائر 2 إلى المليون) يتم خدمتهم فوراً من أقرب سيرفر حافة بدون الوصول لقاعدة البيانات D1 نهائياً (Reads on D1 ≈ 0).

ب. مرآة متصفح العميل (Client IndexedDB):

متصفح الزبون يحفظ ملف JSON الخاص بالمتجر داخل IndexedDB.

في الزيارات التالية، يتم فتح المتجر لحظياً (0ms) من جهاز العميل حتى عند ضعف التغطية.

ج. التحديث عبر "النبضة" (Pulse Invalidation Engine):

عند تغيير التاجر لسعر منتج أو إضافة قسم، يُرسل الباك إند "نبضة خفيفة" (Event) عبر Server-Sent Events (SSE) لـ Edge وللمتصفحات المفتوحة.

النبضة تُعدل القيمة المتغيرة فقط داخل المرآة المحلية بدون إعادة تحميل الصفحة.

آلية إبقاء الاتصال حياً (SSE Keep-Alive Ping):
يلتزم الـ Worker بإرسال "نبضة صامتة" بروتوكولية على هيئة Comment كل 15 ثانية (: ping\n\n) لمنع إغلاق اتصال الـ SSE بسبب الـ Idle Timeouts دون أي تكلفة معالجة على المتصفح.

د. حماية القطعة الأخيرة (Atomic Inventory Allocation):

تصفح المنتجات والسلة يعتمد 100% على المرآة.

عند لحظة الضغط على "تأكيد الطلب"، يتم تنفيذ أمر ذري على Upstash Redis عبر Lua Script:

lua
local current_stock = redis.call('get', KEYS[1])
if tonumber(current_stock) > 0 then
    return redis.call('decr', KEYS[1])
else
    return -1
end
إذا أرجع العداد قراءة ≥ 0 يكتمل الطلب. إذا أرجع -1 يُلغى الطلب وتظهر رسالة "نفدت الكمية".

العملية تستغرق 2 إلى 5 ميلي ثانية وتمنع البيع المزدوج تماماً بدون Locking على D1.

هـ. التعويض الذري وإلغاء الحجز (Compensating Transaction):
في حال نجاح الخصم من Redis ولكن فشلت كتابة الطلب في D1 نهائياً بعد استنفاد محاولات الـ Exponential Backoff، ينفذ الـ Worker فوراً Rollback Script ذري يرجع القطعة لـ Redis مع إصدار Pulse Event صامت للمرآة المحلية (IndexedDB) لإعادة إظهار القطعة للزبائن فوراً لضمان الاتساق التام للبيانات (Eventual Consistency).

🖼️ الباب الثالث: محرك الصور الهجين

3.1 الفلسفة: "الجودة القصوى + الباندويث المجاني"

دمج Cloudinary للضغط والتحسين مع Backblaze B2 للتخزين والبث، عبر تحالف النطاق الترددي مع Cloudflare.

3.2 تدفق العمل

مرحلة الرفع والتنقية:

التاجر يرفع الصورة إلى Cloudinary (بدون ضغط محلي).

Cloudinary يطبق إزالة الخلفية وتحسين الألوان (e_background_removal/f_auto,q_auto).

Worker يسحب النسخة المنقاة ويخزّنها في Backblaze B2.

الصورة الأصلية تُترك في Cloudinary كـ Master Backup.

مرحلة العرض:

الزائر يطلب صفحة المنتج.

Worker يُنشئ رابطاً مباشراً لـ B2 (مع Cache-Control طويل الأمد).

المتصفح يطلب الصورة من B2 عبر Cloudflare CDN.

Cloudflare CDN يخزّن الصورة مؤقتاً على الحافة.

آلية Cache-First للصور:

إنشاء Subdomain (مثل media.dokany.com).

توجيهه عبر Cloudflare (Orange Cloud Proxied) كـ CNAME إلى endpoint الـ B2.

إعداد Cloudflare Cache Rules لتخزين الصور لمدة سنة.

تفعيل Bandwidth Alliance بين Cloudflare و Backblaze.

⚠️ ملاحظات:

استخدم مكتبة خفيفة لـ S3 في Workers (مثل aws4fetch بدلاً من @aws-sdk/client-s3).

أجبِر Header: Cache-Control: public, max-age=31536000, immutable.

إعداد CORS على B2 لتسمح فقط بـ *.dokany.com.

🔐 الباب الرابع: نظام المصادقة "المثلث الذهبي المُحسَّن"

4.1 تدفق تسجيل التاجر (عبر تليجرام)

المستخدم يبدأ البوت (على تليجرام) ويضغط /start.

يطلب البوت: الاسم، اسم المتجر، رقم الهاتف، النيش، الإيميل الإجباري.

يُخزّن البيانات في D1 (users و stores).

يُفعّل زر "🚀 فتح المتجر".

يُرسل رسالة ترحيب.

4.2 القناة الأولى: زر الكيبورد السحري

التاجر يضغط زر "🚀 فتح المتجر".

البوت يستقبل الطلب عبر Webhook.

Worker يُولّد Magic Link (UUID، صلاحية 5 دقائق) ويُرسله.

التاجر يضغط الرابط، Worker يتحقق من Token، يُنشئ JWT Session، ويُوجّه إلى Dashboard.

4.3 القناة الثانية: Magic Link عبر البريد الإلكتروني

عند تعطل تليجرام: التاجر يفتح /login.

يدخل رقم هاتفه.

Worker يُولّد Magic Link (صلاحية 15 دقيقة) ويُرسله عبر Resend.

التاجر يضغط الرابط، Worker يسجل الدخول.

4.4 القناة الثالثة: Backup PIN

في حال فقدان الوصول إلى تليجرام والبريد الإلكتروني.

عند التسجيل: يُطلب تعيين Backup PIN (4 أرقام).

يُشفر PIN باستخدام Web Crypto API + PBKDF2 مع Salt فريد.

عند استخدامه: يُطلب إدخال PIN، يُقارن مع التشفير في D1 (مع Rate Limiting: 5 محاولات خاطئة → قفل مؤقت).

تجاوز القفل: يُرسل Magic Link إلى البريد الإلكتروني لإعادة التعيين.

4.5 إدارة الجلسات

JWT Session: في Cookie (HttpOnly, Secure, SameSite=Lax) مع expires_at (30 يوماً).

Refresh Token: (سيُضاف لاحقاً).

Device Fingerprint: طبقة أمان إضافية.

4.6 مرونة قنوات الدخول

هيكل "المثلث الذهبي" يضمن فصل الاعتمادية عن تليجرام في حالات الطوارئ، مع نسبة إتاحة تتخطى 99.99%.

ب. التابات المتقدمة (Lazy-Loaded Analytics Tabs):

محرك DuckDB-WASM لا يُحمل إطلاقاً عند فتح اللوحة.

يُحمل المحرك فقط في الخلفية عندما يضغط التاجر بنفسه على تاب "التقارير العميقة والتحليلات".

يتم تقسيم التقارير لتابات مستقلة (مثال: تاب "المنتجات الأكثر ربحاً"، تاب "سلوك الزبائن")، وكل تاب يسحب فقط ملف Parquet الخاص به من B2، مما يمنع تجمد الموبايلات الضعيفة ويحافظ على سلاسة التطبيق داخل تليجرام.

تحسين عمليات B2: لتجنب تكلفة عمليات LIST (Class C):

Capture Worker يحفظ أسماء الملفات في D1 أو Redis.

Cleanup Worker يقرأ الأسماء من D1 ويحذفها مباشرة باستخدام DELETE (بدون LIST).

🏰 الباب الحادي عشر: الحصن الرقمي — نظام Rate Limiting متعدد الطبقات

11.1 الفلسفة: "الدفاع المتدرّج بالتكلفة الصفرية"

نظام Rate Limiting يعمل كـ Worker مستقل تماماً (dokany-rate-limiter) عن النظام الأساسي، لتحقيق العزل التام:

لو سقط الحصن، لا تسقط المنصة (Fail-Open).

لو تعرّض الحصن لهجوم، لا يتأثر الـ Core.

المبادئ:

العزل التام: Worker مستقل بـ wrangler.toml خاص.

الذرية المطلقة: Lua Script داخل Redis (ZSET) — مستحيل Race Condition.

Sliding Window Log: أدق من Fixed Window — يمنع هجمات Burst عند حدود النافذة.

Fail-Open المحسوب: إذا تعذّر الوصول للحصن، يُسمح للطلب.

الدفاع المتدرج: 4 طبقات (Global → IP → User → Store).

التكلفة الصفرية: ضمن حدود Upstash Redis و Workers المجانية.

11.2 المكونات الأساسية

المكون	الدور	التقنية
Limiter Worker	استقبال طلبات الفحص	Cloudflare Workers (مستقل)
المخزن الذري	عدّادات Sliding Window	Upstash Redis (ZSET + Lua)
جسر التكامل	ربط Next.js والـ Workers بالحصن	rate-limit-client.ts
سجل الاستراتيجيات	حدود مخصصة لكل عملية	strategies.ts
حارس داخلي	منع استدعاء الحصن من خارج النظام	Header سري X-RL-Token

11.5 آلية العمل

أي نظام يرسل طلب فحص للحصن مع Header X-RL-Token.

Limiter Worker ينفذ Lua Script ذري على Redis لكل طبقة:

ZREMRANGEBYSCORE: تنظيف الطلبات خارج النافذة.

ZCARD: عدّ الطلبات الحالية.

تحت الحد → ZADD (سماح) | فوق الحد → رفض مع retryAfter.

الرد يحمل Headers احترافية:

X-RateLimit-Limit

X-RateLimit-Remaining

X-RateLimit-Reset

قاعدة Fail-Open: أي Timeout أو عطل → يُسمح للطلب مع تسجيل degraded: true.
