📜 الديباجة: فلسفة "الأنماط كبيانات حيوية"
في هذا المخطط، نتعامل مع الأنماط لا كملفات ثابتة تُحمَّل، بل كطبقتين متكاملتين:

طبقة جامدة (Solid Layer): ملفات CSS الأساسية التي تحدد هيكل المكونات وتخطيطها (Header, Product Card, Footer, …). هذه الملفات تُخزَّن على CDN مع immutable Cache، ولا تتغير أبداً.

طبقة حيوية (Liquid Layer): متغيرات :root التي تحدد هوية المتجر البصرية (الألوان، الخطوط، التباعد، الصور، …). هذه المتغيرات تُعامَل كبيانات (Data) وليست كود (Code)، وتُدار عبر نفس آلية "المرآة المزدوجة" المستخدمة للمنتجات والمخزون.

النتيجة: نظام أنماط يفتح في 0ms، يُحدَّث في 0ms، ويشتغل في وضع الأوفلاين، بتكلفة تشغيلية صفرية مطلقة، ودون أي اعتماد على عمليات Purge أو Cold Starts.

✨ المبادئ المعمارية الحاكمة (7 مبادئ)
المبدأ	الوصف
الفصل بين الجامد والحيوي (Static vs Dynamic)	ملفات orchestrator.css والمكونات هي ملفات ثابتة تخزن على CDN بـ max-age=31536000, immutable. متغيرات :root هي بيانات ديناميكية تُحقن محلياً.
البذرة المضمَّنة (Embedded Seed)	الـ HTML الخاص بكل متجر يُولَّد مرة واحدة ويُخزَّن على CDN كـ Edge Snapshot، ويحتوي على متغيرات الثيم الحالية كـ <style id="theme-vars"> و <script id="theme-seed">، لضمان تجربة 0ms حتى للزائر الجديد.
التحديث بالنبضة (Pulse-Driven Updates)	عند تعديل التاجر، يُرسل حدث SSE صغير يحمل {key: value} إلى المتصفح، فيُحدَّث الـ DOM مباشرة (setProperty) ويُحدَّث الـ IndexedDB.
مزامنة التبويبات الذكية (Smart Cross-Tab Sync)	استقبال النبضة في تبويب واحد، ثم بثها عبر BroadcastChannel المخصص للمتجر (dokany_pulse_${storeId}) إلى بقية التبويبات، مع تحديث IndexedDB من تبويب واحد فقط لتجنب التعارضات.
التراجع البسيط (Simple Fallback)	في حال فشل IndexedDB (مثل وضع التصفح الخفي في Safari)، يُستخدم SessionStorage كطبقة تخزين مؤقتة، مع الاحتفاظ بالـ Seed المضمَّن في HTML كضمان أخير.
التكلفة الصفرية للحافة (Zero-Edge Cost)	لا يُستدعى الـ Worker إلا عند تعديل الثيم (نادراً). جميع طلبات الزوار تُخدم من CDN مباشرة (HTML + CSS + Seed)، بدون أي قراءة من KV أو D1.
عزل البيانات الكامل (Strict Multi-Tenant Isolation)	كل متجر له مفتاح مستقل في IndexedDB (theme_${storeId})، وفي SessionStorage، وفي BroadcastChannel، لضمان عدم تداخل بيانات المتاجر.

🔄 تدفق البيانات (Data Flow) — النسخة النهائية
1. الزائر الجديد (أول زيارة)
الزائر يطلب المتجر من المتصفح.

الـ CDN يقدم الـ HTML المخزن كـ Edge Snapshot.

هذا الـ HTML يحتوي مسبقاً على:

<style id="theme-vars"> الذي يحمل جميع متغيرات الثيم الحالية.

<script id="theme-seed"> الذي يحمل نسخة JSON كاملة من الثيم.

يقوم المتصفح بتحميل orchestrator.css من CDN (ملف ثابت بـ immutable).

يقرأ الـ Seed ويخزنه في IndexedDB في الخلفية.

يتم عرض المتجر فوراً (0ms FCP) لأن المتغيرات موجودة في الـ HTML نفسه.

2. الزائر العائد (لديه IndexedDB)
المتصفح يطلب HTML من CDN (يأتيه مع Seed احتياطي لكن لا يُستخدم).

يقوم العميل بقراءة متغيرات الثيم من IndexedDB مباشرة (0ms).

يُنشئ <style id="theme-vars"> محلياً ويُطبق المتغيرات على DOM.

يتم عرض المتجر فوراً (0ms) دون أي طلب للخادم.

3. تحديث الثيم من التاجر (عبر Pulse Event)
التاجر يعدل قيمة (مثل اللون الأساسي) من لوحة التحكم.

Worker يكتب التعديل في D1.

Worker يُعيد توليد :root المتغيرات ويُحدّث KV.

Worker يُعيد توليد HTML Snapshot بالكامل ويُخزّنه على CDN (مرة واحدة).

في نفس الوقت، يُرسل Worker نبضة SSE إلى المتصفحات المفتوحة للتاجر تحمل { "--primary": "#FF0000" }.

المتصفح الذي يستقبل النبضة:

يطبق document.documentElement.style.setProperty("--primary", "#FF0000") فوراً.

يقوم بكتابة التحديث في IndexedDB باستخدام Web Locks API لضمان الكتابة الآمنة.

يبث رسالة عبر BroadcastChannel باسم dokany_pulse_${storeId} تحمل نفس التحديث.

التبويبات الأخرى تستمع للقناة، وعند استقبال الرسالة تطبق setProperty على DOM دون كتابة على IndexedDB.

4. آلية التراجع (Fallback) في حالة فشل IndexedDB
يحاول العميل قراءة الثيم من IndexedDB.

في حال الفشل، يحاول من SessionStorage.

في حال الفشل أيضاً، يستخدم الـ Seed المضمَّن في HTML (الموجود دائماً).

لا يتم اللجوء إلى Edge KV من العميل مطلقاً، للحفاظ على حجم الكود الخفيف وتجنب طلبات إضافية.

إذا كانت جميع الطبقات غير متاحة، يُستخدم الثيم الافتراضي للنظام.

🧩 تفاصيل التنفيذ التقنية (مع التحديثات v5.2)
أ. توليد الـ Edge Snapshot (مع Seed الثيم)
يُولَّد الـ HTML الكامل لكل متجر بواسطة Worker عند:

إنشاء المتجر لأول مرة.

تغيير التاجر للثيم (أو أي بيانات تؤثر على المظهر).

يُخزَّن الـ HTML على Cloudflare CDN مع Cache-Control: public, max-age=31536000, immutable.

يحتوي الـ HTML على:

<style id="theme-vars"> مع جميع متغيرات :root.

<script id="theme-seed" type="application/json"> مع نسخة JSON من الثيم.

روابط لـ orchestrator.css وملفات JavaScript الأساسية.

ضغط الـ Snapshot: لا يتم ضغط الـ HTML يدوياً داخل Worker لتجنب استهلاك CPU Cycles على الحافة. يتم الاعتماد على Brotli/Gzip Automatic Compression المدمج في شبكة Cloudflare CDN عند تقديم الملف للعميل، مما يقلل حجم الـ Snapshot + Seed إلى أقل من 4KB تلقائياً ودون أي تكلفة حوسبة.

ب. آلية التحميل في العميل (Client-Side Bootstrapping)
دالة loadTheme(storeId) تقوم بالخطوات التالية:

محاولة قراءة من IndexedDB (theme_${storeId}).
إذا نجحت، تطبق المتغيرات وتنتهي.
إذا فشلت، تحاول من SessionStorage.
إذا فشلت، تقرأ الـ Seed من عنصر #theme-seed في HTML.
تطبق المتغيرات وتخزنها في IndexedDB و SessionStorage في الخلفية.
في حال عدم وجود Seed، تطبق الثيم الافتراضي.
ج. استقبال Pulse وتحديث الثيم حياً (مقتصر على Dashboard التاجر)
يُمنع منعاً باتاً فتح اتصالات SSE لزوار المتجر. الزوار يستلكون البيانات حصراً عبر (CDN Snapshots + IndexedDB).

الـ SSE مخصص فقط لبيئة التاجر والـ Live Preview (لوحة التحكم والمحرر) حيث لا يتجاوز عدد الاتصالات 50 اتصالاً متزامناً.

يتم إنشاء BroadcastChannel باسم dokany_pulse_${storeId} لكل متجر.

عند تحميل الصفحة، يُقرر التبويب ما إذا كان هو المسؤول عن فتح اتصال SSE (باستخدام علامة في SessionStorage لضمان تبويب واحد فقط).

التبويب الذي يفتح SSE يستقبل الأحداث، ويطبق setProperty، ويُحدّث IndexedDB باستخدام Web Locks (انظر أدناه)، ثم يبث الرسالة للتبويبات الأخرى عبر BroadcastChannel.

التبويبات الأخرى تطبق setProperty فقط دون كتابة في IndexedDB.

د. مزامنة IndexedDB (منع السباقية) — مع Web Locks API
لتجنب أي تعارض في الكتابة أثناء تحديثات Cross-Tab، نستخدم Web Locks API (navigator.locks) كقفل موزع مدمج في المتصفح.

عند كتابة التحديث في IndexedDB (من التبويب الرئيسي)، نطلب قفلًا باسم theme_lock_${storeId} قبل تنفيذ عملية put.

هذا يضمن أن عملية الكتابة تتم بشكل ذري ولا يمكن لأي تبويب آخر أن يكتب في نفس الوقت، حتى في حالات التزامن العالي.

للمتصفحات التي لا تدعم Web Locks، نستخدم Fallback بسيط (دون قفل) مع الحفاظ على آلية version للتقليل من التعارضات.

مثال تنفيذي:

typescript
async function safeUpdateThemeStore(storeId: string, newTheme: ThemeConfig) {
  if ('locks' in navigator) {
    await navigator.locks.request(`theme_lock_${storeId}`, async () => {
      await db.put(`theme_${storeId}`, newTheme);
    });
  } else {
    // Fallback للمتصفحات القديمة (نادر)
    await db.put(`theme_${storeId}`, newTheme);
  }
}
بالإضافة إلى ذلك، نُبقي آلية version كطبقة إضافية للتحقق من التحديثات المتتالية، ونتجنب الكتابة من التبويبات الثانوية (تطبق setProperty فقط).

🚀 المرحلة 8: استراتيجية الهجرة والتراجع الآمن (Zero-Downtime Migration)
الأهمية: هذه المرحلة فائقة الأهمية للإنتاج، وتُطبَّق قبل المراقبة الشاملة (المرحلة 9) لتكون جزءاً من عملية الإطلاق والتحديث.

8.1 محرك مفاتيح الميزات المخصصة لكل متجر (Feature Flags)
إضافة متغيرة use_new_css_engine في قاعدة البيانات / KV لكل متجر.

تطبيق إطلاق تدريجي (Gradual Rollout) عبر الـ Edge Worker:

1% → 10% → 50% → 100%.

آلية العمل:

يقرأ الـ Edge Worker قيمة الـ Flag من KV أو D1.

إذا كان true، يخدم الـ HTML Snapshot الجديد (مع :root و Seed).

إذا كان false، يخدم النظام القديم (مع الحفاظ على التوافق الكامل).

8.2 سكربت تحويل الثيمات (Migration Script Pipeline)
قراءة بيانات الثيمات القديمة من D1.

تحويلها للـ Theme JSON Schema الجديد (مع تطبيق التوريث والتحقق).

التحقق من صحة البيانات المحولة باستخدام Zod Schema.

توليد الـ Edge Snapshots الجديدة وحفظها على CDN.

تحديث Feature Flag للمتجر إلى true بعد نجاح التحويل.

تسجيل الفشل: في حال فشل التحويل، يُسجَّل الخطأ ويُترك المتجر على النظام القديم.

8.3 خطة التراجع الفوري (Rollback Plan)
إبقاء النسخة القديمة من الـ Snapshots محميّة في CDN (مع immutable Cache).

في حال حدوث مشكلة (يتم اكتشافها عبر المراقبة في المرحلة 9)، يتم إطفاء الـ Flag فوراً:

use_new_css_engine = false لكل المتاجر المتأثرة أو لكل المتاجر.

يعود المتجر للنظام القديم فوراً (0ms Downtime) لأن الـ CDN لا يزال يحتفظ بالنسخة القديمة.

يتم إرسال تنبيه فوري لقروب Telegram للمطورين.

🎨 تفاصيل الخطوط المقطوعة (Font Subsetting) — مع نطاق Unicode الشامل
التحسين: تم توسيع نطاق Unicode ليشمل جميع الحالات الممكنة للنصوص العربية والأرقام وعلامات الترقيم، مما يضمن تغطية 100% للغة العربية مع الاحتفاظ بحجم الخط عند ~15KB.

المرحلة 1.3 — الخطوط العربية المقطوعة بالشمل الكامل
ربط خطوط Google Fonts بخاصية font-display: swap;.

تطبيق نطاق الشمول الكامل للغة العربية والرموز والأرقام:

css
unicode-range: 
  U+0600-06FF,        /* Arabic Main Range */
  U+0750-077F,        /* Arabic Supplement */
  U+08A0-08FF,        /* Arabic Extended-A */
  U+FB50-FDFF,        /* Arabic Presentation Forms-A (الحروف في حالات اتصالها المختلفة) */
  U+FE70-FEFF,        /* Arabic Presentation Forms-B */
  U+0660-0669,        /* Arabic-Indic Digits (٠-٩) */
  U+060C, U+061B, U+061F; /* Arabic Punctuation (، ؛ ؟) */
النتيجة: تقليل حجم الخط العربي من 500KB إلى ~15KB مع ضمان عدم حدوث أي اختلال شكلي أو سقوط خطوط:

الحروف الموصولة (أول، وسط، آخر الكلمة).

الأرقام الشرقية.

علامات الترقيم العربية.

الزخارف والكلمات المركبة مثل (ﷺ / ﷼).

المرحلة 6.1 — معالج رفع الخطوط المخصصة
استقبال ملف الخط (.ttf/.otf) من التاجر عبر Dashboard API.

تشغيل Async Job لقطع الخط بـ subset-font للنطاق العربي الشامل (كما هو موصوف أعلاه) والإنجليزي.

توليد ملف .woff2 خفيف (~15KB).

رفعه إلى Backblaze B2 مع كاش immutable.

توليد @font-face ديناميكي مع Fallback صريح لـ Cairo/Tajawal:

css
@font-face {
  font-family: 'CustomFont';
  src: url('https://cdn.dokany.com/fonts/store_123/custom.woff2') format('woff2');
  font-display: swap;
  unicode-range: U+0600-06FF, U+0750-077F, U+08A0-08FF, U+FB50-FDFF, U+FE70-FEFF, U+0660-0669, U+060C, U+061B, U+061F;
}
في حال فشل الـ Job:

يُستخدم الخط الافتراضي (Cairo/Tajawal) دون تأثير على تجربة المستخدم.

يُسجَّل الخطأ في السجلات ويُرسل تنبيه للمطورين.

📊 مقاييس الأداء والتكلفة
المقياس	القيمة المستهدفة	كيفية تحقيقها

عمليات Purge	صفر	لا نحتاج لمسح الكاش، نُحدّث Snapshot فقط
🧪 استراتيجية الاختبار
اختبارات الوحدة (Unit): دوال توليد :root، التوريث، التحقق من صحة الألوان (Vitest / Jest).

اختبارات التكامل (Integration): تدفق Seed → IndexedDB → DOM (Vitest + JSDOM).

اختبارات المزامنة (Sync): Pulse + BroadcastChannel + Web Locks + تحديثات متزامنة (Vitest + Fake Timers + mock Web Locks).

اختبارات الأداء (Performance): قياس وقت FCP، حجم CSS، استهلاك الذاكرة (Lighthouse, WebPageTest).

اختبارات التوافق (Compatibility): المتصفحات المختلفة (Chrome, Safari, Firefox) وسلوك Incognito (BrowserStack, Playwright).

اختبارات الهجرة (Migration): اختبار تحويل الثيمات القديمة إلى Schema الجديد والتأكد من تطابق المخرجات (Vitest).

هذا المخطط المعماري لنظام الأنماط (v5.2) يُغلِق كافة الثغرات المحددة في المراجعات السابقة، ويُضيف تحسينات حاسمة للإنتاج:

يُدمج الأنماط مع معمارية المرآة المزدوجة، محولاً إياها إلى بيانات حيوية تُتزامن.

يلغي تماماً الحاجة إلى عمليات Purge أو إعادة توليد CSS عند كل تعديل.

يُحرّر الـ Worker من عبء معالجة طلبات الزوار، مما يُبقي التكلفة عند $0.

يُقدّم تجربة 0ms حتى للزائر الجديد، بفضل الـ Seed المضمَّن في HTML والضغط التلقائي من CDN.

يدعم الأوفلاين بسلاسة، ويستمر في العمل حتى عند انقطاع النت.

يُبسط الترميز (Fallback) بطبقة واحدة فقط (SessionStorage)، مما يُقلل حجم الكود.

يضمن سلامة الكتابة في IndexedDB باستخدام Web Locks API، مما يمنع أي تعارضات بين التبويبات.

يُحدد استخدام SSE للتاجر فقط، مما يحافظ على صفر اتصالات للزوار ويُبقي الاستهلاك ضمن الحدود المجانية.

يُغطي 100% من اللغة العربية عبر نطاق Unicode الشامل، مع الحفاظ على حجم الخط عند ~15KB.

يُتيح هجرة تدريجية وآمنة (Zero-Downtime) مع Feature Flags وخطة Rollback فورية.

بهذا، تصبح "دكاني" أول منصة SaaS في العالم تمتلك نظام أنماط "صفري التكلفة، صفري الزمن، صفري التعقيد، صفري التعارض، صفري التوقف، صفري الثغرات" — وهو امتداد طبيعي لرؤيتها المعمارية الشاملة. 🚀
