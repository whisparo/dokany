🏛️ دكاني - الدستور النهائي لنظام الأخطاء الخالد (الإصدار 9.1 - النسخة المعمارية القطعية النهائية المُحكمة)
الإصدار: 9.1 (النسخة المعمارية القطعية - المراجعة النهائية المُحكمة)
الهوية: نظام إدارة أخطاء استباقي (Proactive Error Management System) يعمل على بيئة Cloudflare Edge، يجمع بين معالجة الاستثناءات، مراقبة الأداء، والشفافية الكاملة للمستخدم، مع تكلفة تشغيلية صفرية في الأوقات العادية، ونظام مراقبة صحية منفصل بالكامل، وآلية تخزين فورية مقاومة للانهيار.

📜 الديباجة: فلسفة "النظام الذي لا يموت بصمت" (The Never-Silent-Death Philosophy)
نظام الأخطاء هو الجهاز العصبي المركزي للمنصة. هدفه ليس فقط إخبارك بأن شيئاً ما قد مات، بل تنبيهك بأن شيئاً ما على وشك الموت (البطء)، وتقديم تجربة سلسة للمستخدم حتى في أسوأ الظروف.

المبدأ الأسمى: لا يمكن للنظام أن يموت بصمت. يجب أن تكون هناك عين ثالثة تراقب المُراقب نفسه.

المبادئ الحاكمة الإثنا عشر
المبدأ	الوصف
الحركة عند الخطأ فقط	لا يُستهلك أي مورد (Redis، QStash) إلا عند حدوث خطأ فعلي. في الأوقات العادية (99.9% من الوقت)، الاستهلاك = صفر.
الكتابة الفورية القطعية	كل خطأ يُكتب فوراً في Backblaze B2 (تخزين دائم) قبل أي معالجة أخرى. ضمان عدم فقدان أي خطأ حتى لو تعطل الـ Worker فجأة.
الاستباقية	رصد البطء قبل أن يتحول إلى فشل (Performance Sentry) مع توليد تنبيهات PERF_001.
الفصل التام للمراقبة	مراقبة صحة الـ Worker تتم من خارج المنظومة (عبر Uptime Robot) لضمان عدم وجود نقطة فشل واحدة.
الاقتصاد في الإرسال	الأخطاء غير الحرجة تُجمّع وتُرسل دفعة واحدة كل 10 دقائق عبر QStash لحماية باقة تليجرام و Redis.
التجميع الذكي	تجميع الأخطاء المتشابهة في "حادثة" واحدة (Incident Aggregation) لتجنب إغراق قنوات التليجرام، مع الاحتفاظ بـ First/Last Sample لتشخيص دقيق.
التكلفة الصفرية المطلقة	جميع المكونات ضمن حدود الخدمات المجانية (B2، Workers، Upstash Redis Free Tier، QStash Free Tier).
التوافق مع Edge	جميع المكونات تعمل في بيئة Cloudflare Workers مع استخدام عمليات أرخص وتجنب عمليات LIST المكلفة.
المرونة في الفشل	فشل إرسال التنبيه الفوري لا يمنع وصوله لاحقاً عبر المعالج الخلفي (Retry + Fallback).
الشفافية للمستخدم	فصل الرسائل الموجهة للمستخدم (userMessage) عن التفاصيل التقنية (technicalMessage).
الصمت الانتقائي	بعض الأخطاء (مثل فشل تحديث Cache) تُسجل في B2 فقط دون إرسال تنبيهات (Silent Errors)، مع تقرير يومي مُلخص.
التخزين المضغوط	ضغط ملفات الأخطاء في B2 باستخدام gzip لتوفير المساحة وزيادة سرعة القراءة.

1.3 السياق (context.ts) - Hybrid Context Management 🛡️
⚠️ ملاحظة حرجة: في Cloudflare Workers، دعم node:async_hooks يعتمد على تفعيل compatibility_flags = ["nodejs_compat"]. ومع ذلك، في بيئة Serverless Execution، استخدام Context Passing الصريح أو ربط الـ Context عبر Hono.js (c.set / c.get) يكون أضمن 100% ويمنع أي تسرب للـ Request Context بين الطلبات المختلفة.

الحل المعتمد (Hybrid Approach):

typescript
// ✅ 1. تفعيل nodejs_compat في wrangler.toml
// compatibility_flags = ["nodejs_compat"]

import { AsyncLocalStorage } from 'node:async_hooks';

export interface ErrorContext {
  correlationId: string;
  storeId?: string;
  userId?: string;
  breadcrumbs: string[]; // آخر 10 أحداث
  startTime: number;
  path?: string;
  method?: string;
  ip?: string;
}

// ✅ 2. استخدام AsyncLocalStorage للـ Internal Helpers والـ Logger
const contextStore = new AsyncLocalStorage<ErrorContext>();

export function runWithContext<T>(context: ErrorContext, fn: () => T): T {
  return contextStore.run(context, fn);
}

export function getContext(): ErrorContext | undefined {
  return contextStore.getStore();
}

export function addBreadcrumb(message: string, data?: Record<string, unknown>): void {
  const ctx = getContext();
  if (!ctx) return;
  const entry = `${new Date().toISOString()} - ${message}`;
  ctx.breadcrumbs.push(entry);
  if (ctx.breadcrumbs.length > 10) ctx.breadcrumbs.shift();
}

1.4 المُنقي (sanitizer.ts) - أمان البيانات
typescript
const SENSITIVE_KEYS = ['password', 'token', 'secret', 'cookie', 'authorization', 'credit_card', 'cvv'];

export function sanitizeObject(obj: Record<string, unknown>): Record<string, unknown> {
  return Object.fromEntries(
    Object.entries(obj).map(([key, value]) => {
      if (SENSITIVE_KEYS.some(k => key.toLowerCase().includes(k))) {
        return [key, '[REDACTED]'];
      }
      if (typeof value === 'object' && value !== null) {
        return [key, sanitizeObject(value as Record<string, unknown>)];
      }
      return [key, value];
    })
  );
}

🛠️ الباب الثالث: تفاصيل التنفيذ المتقدمة (بدون أكواد)
3.1 المُخزن الفوري (B2 Store) – القلب النابض المُحسَّن
الهدف: ضمان عدم فقدان أي خطأ، حتى في أسوأ السيناريوهات (Crash مفاجئ للـ Worker)، مع تحسين الأداء والتكلفة.

التنفيذ:

كتابة الملف في B2:

إنشاء ملف JSON فريد:

text
errors/raw/2026-07-07/error_1720368000000_abc123.json
ضغط الملف بـ gzip قبل الكتابة (توفير 70-80% من المساحة).

استخدام Content-Encoding: gzip في الـ Headers.

استخدام Bandwidth Alliance بين Cloudflare و Backblaze (تحميل مجاني).

إدارة قائمة الانتظار (النقطة الفارقة):

لا يتم استخدام LIST Operations في B2 (مكلفة وبطيئة).

بدلاً من ذلك: بعد كتابة الملف في B2، يتم دفع (LPUSH) مفتاح الملف إلى Redis List باسم error_queue.

هذا يحول عمليات LIST المكلفة إلى عمليات GET (أرخص بكثير).

سياسة TTL الصارمة:

يجب ألا يتجاوز TTL لأي مفتاح مؤقت في Redis حاجز 24 ساعة كحد أقصى.

الاعتماد الأساسي على B2 لتخزين الـ Logs والـ Payload العالية (10GB مجاناً بدون TTL قسري).

يقتصر دور Redis فقط على الـ Key Pointers والحالات اللحظية (Ephemeral Metadata).

التكلفة المحسوبة:

LIST واحدة على 1000 ملف = 1000 عملية Class C (تستهلك حصتك اليومية).

النظام الجديد: لكل خطأ، عملية PUT واحدة (Class B) + عملية LPUSH واحدة (Redis مجانية) + عملية GET واحدة (Class B) عند المعالجة. توفير 95% من التكلفة.

3.2 المعالج الخلفي (Background Processor) – مع Retry و Fallback
الهدف: فصل المعالجة الثقيلة عن مسار الطلب الرئيسي مع ضمان وصول 100% للتنبيهات.

التنفيذ:

جدولة QStash:

مهمة Cron تعمل كل 10 دقائق.

مع تفعيل Retry تلقائي: 3 محاولات بتأخير (5 دقائق، 15 دقيقة، ساعة).

آلية العمل:

يقرأ المفاتيح من error_queue في Redis باستخدام RPOP (إزالة واسترجاع من النهاية).

لكل مفتاح، يجلب الملف من B2 باستخدام GET (يفك ضغطه).

يقوم بـ:

تحديث عدادات Redis (للتحليل).

التحقق من الـ Incident Aggregation (في Redis بمفتاح incident:${code} مع TTL 5 دقائق).

إرسال إلى تليجرام (مع Rate Limiting).

إذا نجح: يحذف الملف من B2 (أو ينقله إلى processed/).

إذا فشل: ينقل الملف إلى errors/failed/ ويحتفظ بالمفتاح في Redis لـ Retry لاحقاً (مع حد أقصى 3 محاولات).

آلية Retry الذكية:

تخزين retry_count في الملف (أو في Redis).

بعد 3 محاولات فاشلة، يُرسل تنبيه "حادث" (Incident) إلى قروب الإدارة.

الميزة التنافسية: حتى لو فشل إرسال التليجرام الفوري (في المسار السريع)، يبقى الملف في raw/ وسيُرسل عبر المعالج الخلفي. ضمان وصول 100% للتنبيهات.

3.3 Incident Aggregation – منع إغراق التليجرام (مع First/Last Sample)
الهدف: تجميع الأخطاء المتشابهة في "حادثة" واحدة لتجنب إغراق قنوات التليجرام، مع الاحتفاظ بعينات كافية لتشخيص السبب الجذري.

التنفيذ:

إنشاء incident_id:

text
incident:${code}:${storeId}
في Redis:

INCR incident:DB_001:store_123

EXPIRE incident:DB_001:store_123 300 (5 دقائق)

تخزين First Sample و Last Sample:

incident:DB_001:store_123:first ← أول خطأ

incident:DB_001:store_123:last ← آخر خطأ

incident:DB_001:store_123:count ← العدد الإجمالي

عند الإرسال:

إذا كان العداد = 1، أرسل الرسالة كاملة (مع First Sample).

إذا كان العداد > 1، لا ترسل (تكتفي بزيادة العداد وتحديث Last Sample).

بعد 5 دقائق، أرسل رسالة تلخيصية:

text
📊 Incident Report
🔴 Code: DB_001
🏪 Store: store_123
📦 Count: 23 errors in 5 minutes

📌 First Sample: { ... }
📌 Last Sample: { ... }
الميزة: تخفيض عدد رسائل التليجرام من آلاف إلى 1-2 رسالة كل 5 دقائق، مع الحفاظ على عينات دقيقة لتشخيص المشكلة.

3.4 المُنفذ الآمن (Safe Executor) – مع حارس الزمن و Route Thresholds
الهدف: غلاف آمن للعمليات مع مراقبة الأداء وإعادة المحاولة الذكية، مع مرونة في تحديد حدود الأداء لكل Route.

التنفيذ:

توقيت التنفيذ:

typescript
const start = performance.now();
const result = await fn();
const duration = performance.now() - start;
حارس الزمن (Performance Sentry) مع Route Thresholds:

جدول حدود الأداء المخصصة:

Route Pattern	Slow Threshold	Critical Threshold
/api/checkout	2000ms	3000ms
/api/health	200ms	500ms
/api/search	300ms	800ms
/api/orders	500ms	1000ms
* (Default)	1000ms	2000ms
إذا تجاوز الزمن الـ slowThreshold → توليد PERF_001 (تحذير).

إذا تجاوز الزمن الـ criticalThreshold → توليد PERF_003 (حرج).

إعادة المحاولة (Retry):

إذا كان الخطأ قابل للمحاولة (retryable: true):

تأخير تصاعدي مع Jitter: Math.pow(2, attempts) * 200 + Math.random() * 100.

بعد 3 محاولات فاشلة، يُرمى الخطأ إلى المتصل مع رسالة مناسبة.

القيمة الافتراضية (Fallback):

إذا تم توفير fallbackValue، يُرجعه بدلاً من إسقاط التطبيق.

Source Maps التلقائي: معرفة السطر الحقيقي للخطأ في الكود المصدر بدلاً من Stack Trace المشفر.

التكلفة الصفرية المطلقة: جميع المكونات ضمن حدود الخدمات المجانية، مع تحسين العمليات لتجنب العمليات المكلفة.

دكاني Error System ينافس Sentry و Datadog في العقلية، لكن بـ $0 تكلفة، وخصوصية كاملة (بياناتك في B2)، وسرعة فائقة (لأن كل شيء على Edge).

مراقبة خارجية: حتى لو تعطلت كل الـ Workers، ستُعلم بذلك عبر Uptime Robot.

قابلية التوسع: صُمم لخدمة ملايين الأخطاء يومياً مع بقاء التكلفة صفراً.
