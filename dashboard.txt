تُعد لوحة تحكم التاجر (Dashboard) كياناً مستقلاً تماماً عن متجر الزبون (Storefront) من حيث:

هيكل الكود (Code Isolation): مجلدات منفصلة، وميزات معزولة، ولا يوجد أي تداخل في شجرة المكونات.

إدارة الحالة (State Management): تعتمد على TanStack Query كطبقة أساسية لإدارة البيانات، التزامن، والتخزين المؤقت، مع Zustand للحالة العابرة (مثل التبويب النشط، حالة المودال)، و IndexedDB كتخزين محلي غير متزامن.

الاتصال الحي (Real-time): تمتلك محرك نبضات (SSE) خاصاً بها مع Composite Key و Master Tab Pattern، ولا تشارك أي اتصال مع الزبائن.

الأمان (Security): طبقة حماية مستقلة مع مصادقة صارمة، وعزل تام للبيانات عبر store_id، و Rate Limiting في الـ Middleware.

الهدف الأسمى: تقديم تجربة "تعديل فوري، انعكاس آني، وصفر اعتماد على اتصالات الزبائن"، مع بقاء التكلفة التشغيلية عند $0 حتى مع نمو آلاف التجار.

🎨 المبادئ المعمارية الحاكمة (Dashboard-Specific Pillars)
1. العزل التام للواجهة (Clean Overlay & Route Isolation)
جميع مسارات الداشبورد تبدأ بـ (dashboard) في Next.js App Router، مما يسمح بتطبيق Middleware خاص (فحص JWT، التحقق من store_id، Rate Limiting).

لا يمكن الوصول لأي مسار داخلي (/dashboard/*) إلا عبر جلسة مصادقة صالحة، ويُمنع تخزين هذه الصفحات في الـ Edge Cache (عكس الـ Storefront).

2. التعديل التفاؤلي عبر TanStack Query (Pure TanStack Optimistic UI)
القاعدة الذهبية: المستخدم (التاجر) لا ينتظر الخادم أبداً.

آلية العمل: استخدام useMutation مع onMutate لتحديث الـ Cache فوراً (0ms)، و onError للـ Rollback التلقائي، و onSettled لإعادة التحقق (Revalidate).

التعامل مع التعديلات المتتالية: استخدام queryClient.cancelQueries() لإلغاء أي طلبات سابقة على نفس الكيان، وأخذ Snapshot من الـ Cache قبل التعديل لاستخدامه في Rollback.

انقطاع الشبكة: الاعتماد على persistQueryClient مع createAsyncStoragePersister لتخزين الـ Cache في IndexedDB، مع retry تلقائي عند عودة الاتصال.

3. اليقظة الحصرية مع Master Tab Pattern (Exclusive Real-Time Pulse)
تُستخدم تقنية SSE (Server-Sent Events) حصرياً مع لوحة التحكم لمتابعة الطلبات الجديدة.

Master Tab Pattern:

التبويب الأول (Master) يفتح اتصال SSE ويكتب في IndexedDB.

التبويبات الأخرى تستخدم BroadcastChannel (مع Fallback لـ localStorage) للاستماع للتحديثات.

Composite Key: ${storeId}:${tabId} لمنع تعارض التبويبات.

حد أقصى 5 اتصالات لكل storeId، مع رفض أي اتصال إضافي بـ 429 Too Many Requests.

Stateless SSE Worker: يُغلق الاتصال تلقائياً بعد 30 ثانية من الخمول.

Polling Fallback: إذا تعذر فتح SSE، يتحول العميل إلى Polling مع Exponential Backoff (حد أقصى 10 ثوانٍ) مع Jitter عشوائي، وإعادة اتصال فوري عند عودة navigator.onLine.

4. الإبطال القائم على الإصدار (Version-Based Invalidation)
بدلاً من Cache Purge: كل Edge Snapshot يحمل version (رقم متزايد في KV).

العميل يُرسل If-None-Match: version_{version} في طلب Snapshot.

إذا كان version مطابقاً، يرد الـ Worker بـ 304 Not Modified (بدون إعادة توليد).

إذا كان مختلفاً، يُعيد الـ Worker Snapshot الجديد ويُحدّث version.

النتيجة: لا حاجة لمسح الكاش نهائياً (caches.default.delete يُلغى)، مما يُقلل التكلفة والـ Latency بنسبة 99%.

5. المصدر الوحيد للحقيقة مع Atomic Updates (Single Source of Truth)
D1 هي الفيصل النهائي لأي عملية كتابة.

Atomic Updates: استخدام UPDATE ... WHERE id = ? AND store_id = ? مباشرة (مع Drizzle ORM) لضمان الذرية ومنع Race Conditions.

التحقق من عدد الصفوف المتأثرة (returning أو rowsAffected) لتحديد نجاح أو فشل العملية.

2. التعديل التفاؤلي مع TanStack Query (النمط القياسي)
يُستخدم هذا النمط في كل useMutation داخل الداشبورد.

typescript
// مثال: تحديث سعر المنتج
const updateProductMutation = useMutation({
  mutationFn: (data: UpdateProductData) => updateProductPrice(data),
  
  // 1. 🚀 Optimistic Update (0ms)
  onMutate: async (newData) => {
    // أ. إلغاء أي طلبات سابقة على نفس المنتج (لمنع الـ Race Conditions)
    await queryClient.cancelQueries({ 
      queryKey: ['product', newData.productId] 
    });

    // ب. أخذ Snapshot من الـ Cache الحالي (للـ Rollback)
    const previousProduct = queryClient.getQueryData(
      ['product', newData.productId]
    );

    // ج. تحديث الـ Cache فوراً بالبيانات الجديدة (Optimistic UI)
    queryClient.setQueryData(
      ['product', newData.productId], 
      (old: any) => ({ ...old, price: newData.newPrice })
    );

    // د. إرجاع الـ Snapshot لاستخدامه في حالة الفشل
    return { previousProduct };
  },

  // 2. ❌ Rollback عند فشل الطلب
  onError: (error, newData, context) => {
    // إعادة الـ Cache إلى الحالة السابقة
    queryClient.setQueryData(
      ['product', newData.productId],
      context?.previousProduct
    );
    // إظهار تنبيه للتاجر
    showToast('❌ فشل تحديث السعر، يرجى المحاولة مجدداً');
  },

  // 3. ✅ تحديث نهائي عند النجاح أو الفشل
  onSettled: (data, error, newData) => {
    // إعادة التحقق (Revalidate) من الخادم للتأكد من التطابق
    queryClient.invalidateQueries({ 
      queryKey: ['product', newData.productId] 
    });
  },
});
لماذا هذا النمط هو الأفضل؟

لا حاجة لـ OptimisticUpdateManager خارجي (تجنب Duplication of Truth).

cancelQueries يمنع أي تحديثات متداخلة (Rapid Consecutive Edits) من التسبب في سباقية.

الـ Rollback يحدث تلقائياً عند أي خطأ (4xx/5xx).

      eventSource.close();
    };

// Worker: SSE Handler
const activeConnections = new Map<string, ReadableStreamDefaultController>();
const MAX_CONNECTIONS_PER_STORE = 5;

async function handleSSE(request: Request, storeId: string) {
  const url = new URL(request.url);
  const tabId = url.searchParams.get('tabId') || 'default';
  const connectionKey = `${storeId}:${tabId}`;

  // ✅ التحقق من الحد الأقصى للاتصالات
  let count = 0;
  for (const key of activeConnections.keys()) {
    if (key.startsWith(`${storeId}:`)) count++;
  }
  if (count >= MAX_CONNECTIONS_PER_STORE) {
    return new Response('Too many connections', { status: 429 });
  }

  const { 0: response, 1: controller } = new TransformStream();
  activeConnections.set(connectionKey, controller);

  // ✅ إغلاق تلقائي بعد 30 ثانية خمول
  const timeoutId = setTimeout(() => {
    controller.close();
    activeConnections.delete(connectionKey);
  }, 30000);

  // ✅ Keep-Alive كل 20 ثانية
  const keepAlive = setInterval(() => {
    try { controller.enqueue(`: ping\n\n`); } catch { clearInterval(keepAlive); }
  }, 20000);

  request.signal.addEventListener('abort', () => {
    clearTimeout(timeoutId);
    clearInterval(keepAlive);
    activeConnections.delete(connectionKey);
  });

  return new Response(response, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
    },
  });
}

// إرسال نبضة للاتصالات المفتوحة
async function sendSSEPulse(storeId: string, data: any) {
  const events: Promise<void>[] = [];
  for (const [key, controller] of activeConnections) {
    if (key.startsWith(`${storeId}:`)) {
      events.push(
        new Promise(resolve => {
          try { controller.enqueue(`data: ${JSON.stringify(data)}\n\n`); } catch {}
          resolve();
        })
      );
    }
  }
  await Promise.all(events);
}
ج. Polling Fallback (عند فشل SSE)
typescript
// AdaptivePoller.ts
class AdaptivePoller {
  private backoff = 1000;
  private maxBackoff = 10000;
  private isPolling = false;

  async start(storeId: string) {
    this.isPolling = true;
    await this.poll(storeId);
  }

  stop() { this.isPolling = false; }

  private async poll(storeId: string) {
    if (!this.isPolling) return;

    if (!navigator.onLine) {
      await this.waitForOnline();
      this.backoff = 1000;
    }

    try {
      const res = await fetch(`/api/pulse?storeId=${storeId}&ts=${Date.now()}`, {
        headers: { 'If-None-Match': this.getLastETag() }
      });

      if (res.status === 304) {
        this.backoff = Math.min(this.backoff * 1.5, this.maxBackoff);
      } else if (res.ok) {
        const events = await res.json();
        this.handleEvents(events);
        this.backoff = 1000;
      } else {
        throw new Error('Server error');
      }
    } catch {
      this.backoff = Math.min(this.backoff * 2, this.maxBackoff);
      this.backoff += (Math.random() * 2000) - 1000; // Jitter
    }

    setTimeout(() => this.poll(storeId), this.backoff);
  }

  private waitForOnline(): Promise<void> {
    return new Promise(resolve => {
      if (navigator.onLine) return resolve();
      window.addEventListener('online', () => resolve(), { once: true });
    });
  }
}
د. Cross-Tab Bus (BroadcastChannel + Fallback)
typescript
// CrossTabBus.ts
class CrossTabBus {
  private channel: BroadcastChannel | null = null;
  private listeners: Set<(data: any) => void> = new Set();

  constructor(private channelName: string) {
    if ('BroadcastChannel' in window) {
      this.channel = new BroadcastChannel(channelName);
      this.channel.onmessage = (e) => this.notify(e.data);
    } else {
      // Fallback للمتصفحات القديمة
      window.addEventListener('storage', (e) => {
        if (e.key === this.channelName && e.newValue) {
          this.notify(JSON.parse(e.newValue));
        }
      });
    }
  }

  postMessage(data: any) {
    if (this.channel) {
      this.channel.postMessage(data);
    } else {
      localStorage.setItem(this.channelName, JSON.stringify(data));
      setTimeout(() => localStorage.removeItem(this.channelName), 100);
    }
  }

  onMessage(callback: (data: any) => void) {
    this.listeners.add(callback);
  }

  private notify(data: any) {
    for (const listener of this.listeners) listener(data);
  }
}

// Worker: Snapshot Handler
async function getSnapshot(storeId: string, clientVersion?: number) {
  const currentVersion = await env.KV.get(`snapshot_version:${storeId}`);
  const currentData = await env.KV.get(`snapshot:${storeId}`);

  // ✅ إذا كان الإصدار مطابقاً، يُرجع 304 (بدون بيانات)
  if (clientVersion && clientVersion === parseInt(currentVersion || '0')) {
    return new Response(null, { status: 304 });
  }

  // توليد Snapshot جديد (إذا لم يكن موجوداً أو الإصدار أقدم)
  const newData = await generateSnapshot(storeId);
  const newVersion = (parseInt(currentVersion || '0') || 0) + 1;

  await env.KV.put(`snapshot:${storeId}`, JSON.stringify(newData));
  await env.KV.put(`snapshot_version:${storeId}`, newVersion.toString());

  return new Response(JSON.stringify(newData), {
    headers: { 'ETag': `version_${newVersion}` }
  });
}

// fetchSnapshot.ts
async function fetchSnapshot(storeId: string) {
  const cachedVersion = localStorage.getItem(`snapshot_version_${storeId}`);

  const response = await fetch(`/api/snapshot/${storeId}`, {
    headers: { 'If-None-Match': `version_${cachedVersion || '0'}` }
  });

  if (response.status === 304) {
    return; // لا تغيير، استخدم الـ Cache المحلي
  }

  const data = await response.json();
  const etag = response.headers.get('ETag');
  const newVersion = etag?.replace('version_', '');
  
  if (newVersion) {
    localStorage.setItem(`snapshot_version_${storeId}`, newVersion);
    // تخزين البيانات في TanStack Query Cache
    queryClient.setQueryData(['snapshot', storeId], data);
  }
}

const ratelimit = new Ratelimit({
  redis: kv,
  limiter: Ratelimit.slidingWindow(100, '1m'), // 100 طلب/دقيقة لكل Session
});

export function middleware(request: NextRequest) {
  if (request.nextUrl.pathname.includes('/dashboard')) {
    const session = request.cookies.get('session');
    if (!session || !isValidJWT(session.value)) {
      return NextResponse.redirect('/auth/login');
    }

    // ✅ Rate Limiting
    const sessionId = session.value;
    const { success } = await ratelimit.limit(sessionId);
    if (!success) {
      return new Response('Too Many Requests', { status: 429 });
    }

    const storeId = extractStoreId(session.value);
    const response = NextResponse.next();
    response.headers.set('x-store-id', storeId);
    return response;
  }
}

هذه الوثيقة (الإصدار 1.2) تُعرّف "داشبورد دكاني" كمنصة مصغرة ومستقلة بذاتها، وتجمع بين:

أبسط وأقوى إدارة للحالة: الاعتماد على TanStack Query وحده لـ Optimistic Updates، Offline Queue، و Retry (مع createAsyncStoragePersister و idb-keyval).

سرعة فائقة: 0ms في التفاعل اليومي بفضل التعديلات التفاؤلية.

مرونة قصوى: تعمل حتى في وضع الأوفلاين وتُزامن تلقائياً.

تكلفة صفرية: انعدام الاتصالات المفتوحة للزبائن، وتقليل عمليات الخادم إلى أقل من 5% من الحدود المجانية.

أمان منيع: عزل تام، مصادقة صارمة، Idempotency، و Rate Limiting.

موثوقية عالية: Version-based Invalidation يُلغي الحاجة لـ Cache Purge، و Master Tab Pattern مع Polling Fallback يضمن وصول الأحداث.

بهذا الميثاق، تصبح لوحة التحكم العمود الفقري الذكي للمنصة، القادر على الصمود أمام آلاف التجار مع الحفاظ على تجربة تُنافس التطبيقات الأصلية (Native Apps)، وبتكلفة تشغيلية تساوي صفراً مطلقاً. 🚀

🟡 المرحلة 3: النواة المعمارية للكتالوج والواجهات الذكية (مع العمارة الهرمية والـ Double Cache)
3.1 تأسيس موديول الأقسام وتكامل الـ Double-Edge Caching Layer
الـ D1 Schema & Composite Ordering: إضافة جدول الأقسام بدعم التداخل الهرمي (parentId) وحقل الترتيب (sortIndex) لضمان الفرز في الـ Source of Truth (Cloudflare D1).

إستراتيجية الـ Double-Edge Caching Layer:

Layer 2 (Edge Cache / KV Snapshots): عند تعديل أو إضافة قسم/منتج، تقوم الـ Orchestrator بإنشاء Snapshot كامل ومضغوط للهيكل والمنتجات وتحديثه في Cloudflare KV، مع رفع Version Key خاص بالمتجر. الاستعلامات القادمة من الـ Front/Dashboard تقرأ مباشرة من KV لتوفير استجابة شبه لحظية وتقليل تكلفة القراءة من D1 إلى 0$.

Layer 1 (Client/Browser Cache): مزامنة الـ KV Snapshot مع متصفح العميل عبر TanStack Query + IndexedDB Persister (createAsyncStoragePersister مع idb-keyval). يتم الاستعلام بإرسال If-None-Match: version_{v}؛ إذا لم يتغير الإصدار يُرجع الخادم 304 Not Modified وتُقرأ البيانات محلياً من IndexedDB بـ 0ms Latency.

الـ Index Gateway (categories-management/index.ts): إنشاء الـ Index كبوابة خفيفة تصدر الـ API والـ Public Actions، وتحيل المعالجة والتتبع للأوركسترا المركزية ورابطها بـ Background Error Queue، مع إدارة إبطال وتحديث كاش الـ KV/IDB تلقائياً (Invalidation Flow).

الـ Server Actions & Hooks: بناء الأكشنز الذرية (Atomic) مع دعم TanStack Query لتحديث الهيكل التفاؤلي (Optimistic UI) وإدارة الـ Write-Through لـ D1 مع تحديث الـ Snapshot في KV.

3.2 الواجهة الهرمية لصفحة المنتجات (app/.../dashboard/products/page.tsx)
شريط الفلترة الهرمي (CategoryFilterRibbon): بناء مكون أفقي يعرض الأقسام الرئيسية والفرعية كـ Tabs منسدلة مع Badges لأعداد المنتجات مباشرة من الـ Flat Index المجلوب من الـ Client IndexedDB Cache.

الجدول الذكي المفلتر (ProductQuickTable): عرض المنتجات المفلترة بحسب القسم المحدد، مع ربطه بـ QuickStockEditor للتعديل الخاطف للمخزون والأسعار، وتمرير التعديلات عبر Optimistic Updates لتحديث الـ IDB فوراً قبل تأكيد الـ KV snapshot من السيرفر.

3.3 حصر بقية مسارات الداشبورد كـ Placeholders
إعداد الهيكل الأساسي للراوتس المتبقية (orders, customers, settings, builder) لتأمين التنقل في الـ Sidebar بدون كسر الـ Router، تمهيداً لربطها بالـ Double-Edge Pipeline في المراحل القادمة.

🔴 المرحلة 4: محرك الطلبات والنبض الحي (Order Engine & Real-time SSE)
4.1 موديول الطلبات وتأثير الـ Double Cache
معالجة العمليات الحسابية: تفعيل الـ index.ts Gateway لموديول الطلبات وتنسيق prepareOrderItems و calculateOrderTotals مع الاعتماد الحصري على الـ Integers للمبالغ المالية لتفادي خطأ Floating Point.

ربط الـ Events بـ Double Cache: استقبال إشارات التغيير عبر SSE يؤدي لإرسال إشارة إبطال خفيفة (Revalidate Version) للـ TanStack Query، لتحديث الـ IndexedDB محلياً إما عبر Diff أو جلب الـ Snapshot المحدث من Cloudflare KV.
